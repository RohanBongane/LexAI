1. Executive Project Overview

What is LexAI?
LexAI is an AI-assisted legal information and document intelligence platform. It allows users to upload complex legal contracts (PDF or DOCX), automatically extracts the text, and leverages Google's Gemini Large Language Model (LLM) to perform deep legal analysis, producing structured executive summaries and clause breakdowns.

What problem does it solve?
Legal documents are notorious for being dense, lengthy, and filled with difficult jargon. Laypeople and legal professionals alike spend excessive time reviewing standard contracts to find obligations, liabilities, and core terms. Furthermore, accessing reliable general legal information often requires expensive consultations. LexAI automates the heavy lifting of document review and provides an instant, AI-driven knowledge base.

Who is it designed for?
LexAI is designed for individuals reviewing personal contracts, small business owners examining vendor agreements, and law students or professionals who need a fast, AI-powered paralegal assistant to highlight key elements of a legal text.

What can a user do with it?
Users can create an account, upload legal documents, view automated AI analyses of those documents, and interact with an AI Chatbot in two distinct modes: 1. Document Chat: Ask specific questions about an uploaded contract (e.g., "What is the termination clause?"). 2. General Legal Chat: Ask broad legal questions which the AI answers by retrieving grounded information from the platform's trusted Knowledge Base.

Why is AI useful in this project?
Traditional software can search for keywords, but only modern LLMs can understand the semantic meaning of a "force majeure" clause even if it's worded differently. AI enables the system to summarize, interpret, and answer natural language questions about dense text.

Disclaimer (As implemented in the project):
LexAI provides AI-generated information for educational and informational purposes only. It is NOT a replacement for a qualified lawyer and does not constitute professional legal advice. Laws vary by jurisdiction and circumstances.

2. Problem Statement

Navigating the legal landscape presents several distinct challenges that LexAI aims to mitigate: - Complexity and Length: Legal documents (contracts, terms of service, NDAs) are lengthy and difficult for non-lawyers to understand. - Hidden Risks: Users struggle to identify important clauses, rights, obligations, and potential liabilities buried in "legalese." - Time Consumption: Traditional document review requires significant manual effort and hours of reading. - Access to Information: Finding relevant, structured, and easy-to-understand legal information is time-consuming and often requires consulting expensive professionals.

5. Technology Stack

The LexAI project utilizes a modern Python-based web architecture.

Frontend

  • HTML5 & CSS3: Standard markup and styling.
  • JavaScript (Vanilla): Handles asynchronous chat requests, markdown rendering, and dynamic UI interactions without the overhead of heavy frameworks.
  • Bootstrap 5: Used for the responsive grid, pre-built UI components (cards, modals, sidebars), and consistent styling.
  • marked.js & DOMPurify: Used to safely render Markdown responses (from Gemini) into HTML on the client side while preventing Cross-Site Scripting (XSS).
  • MathJax: Used to render complex mathematical/logical formulas (like contract equations) output by Gemini in LaTeX format.

Backend

  • Python (3.x): The core programming language powering the backend logic.
  • Flask: A lightweight WSGI web application framework used to route HTTP requests, manage sessions, and render templates.
  • Flask-SQLAlchemy: An Object-Relational Mapper (ORM) that bridges Python objects and the MySQL database.
  • Flask-Login: Manages user sessions, login state, and role-based access control.
  • Flask-Bcrypt: Hashes user passwords securely using the bcrypt algorithm.

Database

  • MySQL (via mysql-connector-python): The primary relational database storing users, documents metadata, analyses, chat histories, and knowledge base articles.
  • ChromaDB: A specialized, locally-hosted Vector Database used entirely for storing and retrieving high-dimensional text embeddings for the RAG system.

AI & Machine Learning

  • Google GenAI SDK (google-genai): Communicates with Google's Gemini API to generate intelligent text analysis and chatbot responses.
  • SentenceTransformers (all-MiniLM-L6-v2): A local NLP model used to convert text (document chunks and queries) into 384-dimensional vector embeddings for semantic similarity search.

Document Processing

  • PyMuPDF (fitz): A high-performance library used to parse and extract raw text from PDF files.
  • python-docx: Used to parse and extract text from Microsoft Word (.docx) files.

Testing

  • Pytest: The testing framework used to run the 86-test suite, ensuring routing, authentication, security, and RAG isolation behave as expected.

6. Technology Concepts for Teammates

To successfully contribute to LexAI, teammates should understand these core concepts:

Flask

Flask is a web framework for Python. Instead of writing raw HTTP servers, Flask allows us to map URLs to Python functions using decorators (e.g., @app.route('/dashboard')). It handles incoming requests, manages cookies/sessions, and returns HTML templates.

MySQL & Relational Databases

A relational database stores data in interconnected tables. LexAI uses MySQL to store structured metadata (like usernames, passwords, file paths, and conversation records). It ensures data integrity through relationships (e.g., a Document belongs to a User).

SQLAlchemy (ORM)

Writing raw SQL queries (like SELECT * FROM users) can be tedious and prone to SQL injection. SQLAlchemy allows us to interact with the database using Python objects (e.g., User.query.all()), automatically translating Python code into safe SQL queries behind the scenes.

Google Gemini API

Gemini is the Large Language Model (LLM) serving as the "brain" of LexAI. When a user uploads a contract, the backend extracts the text and sends it to Gemini via an API key, prompting it to summarize the text. API errors like 429 (Quota Reached) or 503 (Service Unavailable) happen when Google's servers are too busy.

ChromaDB & Vector Databases

Traditional databases search by exact keyword matches. A vector database (like ChromaDB) searches by meaning. When we store a document, we convert it into numbers (vectors). When a user asks a question, we convert the question into numbers and find the document chunks mathematically closest in meaning to the question.

SentenceTransformers (all-MiniLM-L6-v2)

This is the specific AI model that does the conversion from text to numbers (embeddings). We run this locally on the server to avoid paying API costs for embedding generation. It creates a 384-dimensional vector for every chunk of text.

Retrieval-Augmented Generation (RAG)

LLMs like Gemini don't inherently know about a user's private contract, nor do they perfectly memorize specific Indian Contract Law. RAG fixes this: 1. User Question: "What happens if they terminate early?" 2. Search: We search ChromaDB for clauses regarding "early termination" in the user's uploaded document. 3. Retrieve: ChromaDB returns the 3 most relevant paragraphs. 4. Augment & Generate: We send the question PLUS the retrieved paragraphs to Gemini, saying: "Answer the question USING ONLY this text." This guarantees accurate, grounded answers and prevents the AI from hallucinating.

PyMuPDF & python-docx

These libraries open the binary .pdf and .docx files the user uploads and pull out raw text strings that our AI and embedding models can process.

marked.js + DOMPurify

Gemini returns responses formatted in Markdown (using **bold** and ### headings). marked.js converts this to HTML so the browser can style it. However, directly inserting HTML into a webpage is dangerous (a hacker could inject malicious scripts). DOMPurify scrubs the HTML clean before we display it.

8. Complete User Flow

Primary Application Journey

  1. Public Landing Page: Visitor lands on / and views the SaaS-style marketing page.
  2. Authentication: User navigates to /register or /login and authenticates.
  3. Dashboard: User lands on /dashboard, seeing a summary of their uploaded documents.
  4. Document Upload: User navigates to the AI Analysis page and uploads a .pdf or .docx.
  5. Processing: The backend validates the file, extracts text, calculates word/page counts, and chunks/embeds the text into ChromaDB.
  6. Analysis Generation: The backend sends the full text (if within limits) to Gemini to generate an Executive Summary, which is stored in MySQL.
  7. Document Chat: The user opens the Chat UI (/chat), selects the uploaded document, and asks a specific question. The RAG system isolates the search to only that document's vector chunks and generates an answer.

General Legal Chat Journey

  1. The user goes to /chat and selects "General Legal".
  2. The user asks "What is a voidable contract?".
  3. The RAG system searches ChromaDB filtering strictly for source_type: knowledge_base.
  4. It retrieves matching legal concepts curated by the Admin.
  5. Gemini uses those concepts to formulate a highly accurate legal answer. (If Gemini is down, the deterministic fallback parser kicks in to present the KB data cleanly).

13. Document Processing Pipeline

When a user clicks "Upload Document": 1. Validation: document_routes checks if the file is .pdf or .docx and under the 16MB limit. Security checks ensure it's not a disguised script or malware. 2. File Storage: The file is saved securely to uploads/documents/<user_id>/. 3. Text Extraction: document_service processes the binary file, stripping layout and extracting raw unicode text. 4. Statistics: Word counts and page counts are calculated and saved to the documents table in MySQL. 5. Chunking: embedding_service slices the massive string into smaller, overlapping chunks (e.g., 500 words with 50-word overlaps) so context isn't lost across chunk boundaries. 6. Embedding & Indexing: The SentenceTransformer runs on each chunk, generating vectors that are stored in the local chroma_db/ folder, tagged with {"document_id": ID, "user_id": ID} metadata.

14. AI Legal Analysis Pipeline

After a document is processed, LexAI automatically generates a structured analysis.

The Flow: 1. The backend passes the extracted text to ai_service.analyze_legal_document(). 2. A strict system prompt is attached, forcing Gemini to reply in a specific JSON structure. 3. Gemini processes the document and returns the JSON. 4. The backend parses the JSON, creating an Executive Summary and extracting Key Clauses. 5. The data is saved into the document_analysis MySQL table. 6. The analysis.html template renders this data dynamically in the browser.

Error Handling / Resilience: - If Gemini returns 503 Unavailable or 429 Quota Exceeded, the backend catches the error. - The analysis is marked as failed, and the user is shown a friendly error message ("Model experiencing high demand"). - A "Retry Analysis" button appears on the UI, allowing the user to trigger the analysis later without re-uploading the file. - If Gemini returns malformed text instead of JSON, the backend attempts to aggressively clean the string or safely defaults to displaying a raw summary.

15. RAG System Explained

RAG (Retrieval-Augmented Generation) is what prevents LexAI from hallucinating and allows it to securely answer questions about private documents.

The Concept of a Chunk: Language models have token limits. We cannot feed a 500-page document into Gemini for every chat question. Instead, we break the document into "chunks".

The Embedder: all-MiniLM-L6-v2 turns chunks into vectors. Vectors are essentially mathematical coordinates. Sentences with similar meanings get coordinates close to each other.

ChromaDB Retrieval: When a user asks "Who is liable?", that question is embedded into a vector. ChromaDB calculates the mathematical distance between the question vector and all document chunk vectors, returning the top 3 closest chunks.

Document Chat Mode

  • Filtering: ChromaDB query includes where={"document_id": user_selected_id}.
  • Isolation: Because the database validates that document.user_id == current_user.id, User A can never query User B's document chunks.
  • Generation: Gemini receives a prompt: "Use the following extracted document chunks to answer...".

General Legal Chat Mode

  • Filtering: ChromaDB query includes where={"source_type": "knowledge_base"}.
  • Generation: Gemini acts as a legal assistant, grounded only by the approved knowledge base articles.

16. Knowledge Base

The Knowledge Base (KB) is a curated repository of general legal concepts (e.g., "Breach of Contract", "NDAs"). It prevents LexAI from giving unauthorized or wild legal advice by restricting general chat answers to approved topics.

Management & Storage: - Admins can view, add, and delete articles via the /admin interface. - Title and Category metadata is stored in MySQL. - The actual article content is embedded and stored in ChromaDB using source_type: knowledge_base.

KB Seeding (seed_kb.py): To bootstrap the platform, scripts/seed_kb.py iterates through a list of fundamental legal topics. It calls Gemini to generate comprehensive articles for each topic, embeds them, and inserts them into both MySQL and ChromaDB. Due to Gemini's free-tier rate limits (15 requests per minute), the script includes automatic 60-second sleep cycles.

The Deterministic KB Fallback Mechanism: If Gemini goes down (HTTP 503 or 429) during a General Legal Chat, the RAG system intercepts the failure. Because ChromaDB successfully retrieved the relevant KB chunks before the Gemini failure, a custom python parser (construct_fallback_response) kicks in. It deterministically strips Markdown metadata out of the database chunk, isolates the Direct Answer, Key Information, and Remedies based on the user's query keywords, and returns a perfectly formatted Markdown response—ensuring the user still gets a reliable answer without needing the AI generation step!

17. Chat System

The Chat System relies on AJAX requests to provide a seamless, non-reloading interface.

  1. Frontend: chatbot.js intercepts the form submission. It appends a temporary "Loading" bubble and sends a POST /api/chat request containing the message, conversation_id, and document_id.
  2. Backend: The route validates ownership, queries the RAG service, and gets an answer.
  3. Storage: It saves the user's message and the AI's response to the messages MySQL table, associated with a conversation_id.
  4. Return: It returns JSON containing the answer and the sources.
  5. Rendering: chatbot.js passes the answer through marked.js (for Markdown formatting), DOMPurify (for security), and finally calls MathJax to format any embedded mathematical equations (common in contract logic explanations).

18. Authentication & Security

LexAI employs robust security measures: - Password Security: Plaintext passwords are never stored. Flask-Bcrypt hashes passwords with salt. - Session Management: Flask-Login handles HttpOnly session cookies. - Role-Based Access Control (RBAC): Admin routes are protected by an @admin_required decorator. If a normal user tries to access /admin, they are redirected. - Data Isolation: Every single database query for documents or conversations includes .filter_by(user_id=current_user.id). Path traversal attacks (e.g., trying to read ../../etc/passwd) are blocked using werkzeug.utils.secure_filename. - Open Redirect Protection: The login system validates that the next URL is a relative path (local) and not an external malicious site. - Cross-Site Scripting (XSS): DOMPurify aggressively scrubs all AI-generated output on the frontend to ensure no <script> tags are executed.

19. Error Handling

  • HTTP 404 (Not Found): Handled gracefully with a custom 404.html page for browsers, and a standard JSON response for API endpoints.
  • HTTP 413 (Payload Too Large): Triggers if a user uploads a file > 16MB. Returns a friendly flash message.
  • HTTP 429 (Too Many Requests): Used specifically when Gemini hits its rate limit. The chatbot frontend catches this and displays the deterministic fallback or a friendly retry message.
  • HTTP 500/503 (Server/Service Unavailable): Caught during RAG processing. The user is informed that the model is experiencing high demand.

23. Gemini API / Quota

LexAI heavily relies on the Google Gemini API (GEMINI_API_KEY). - The key is configured in the .env file. It acts as a secret password and must never be committed to GitHub. - The AI_MODEL variable defines which Gemini version to use (e.g., gemini-2.5-flash). - Quota / 429 Error: The free tier of Gemini limits users to 15 requests per minute. If you click too rapidly or run the seed script too fast, Google blocks the request. LexAI handles this gracefully. - Service Unavailable / 503 Error: Sometimes Google's servers are overloaded. This is external to LexAI.

  • DB_PASSWORD=YOUR_DB_PASSWORD: Your MySQL password.
  • DB_NAME=lexai_db: The name of the MySQL database.
  • GEMINI_API_KEY=YOUR_GEMINI_API_KEY: Your personal Google AI API key.
  • AI_MODEL=gemini-2.5-flash: The targeted LLM.

(Note: Real keys are strictly excluded from this documentation.)

27. How to Add a New Knowledge Base Article

There are two ways to add articles to the KB: 1. Via UI: Login as an Admin, click "Admin Dashboard" in the sidebar, and use the "Add Knowledge Base Entry" form. This saves the metadata to MySQL and automatically embeds the content into ChromaDB. 2. Via Script: Add a tuple to the kb_topics list in scripts/seed_kb.py and run the script. It will call Gemini to write the article, embed it, and store it.

29. Development Rules for Teammates

  1. Never commit .env: Keep your API keys and passwords safe.
  2. Never run destructive commands: Do not wipe the database to fix a small issue.
  3. Never point tests to production: Ensure conftest.py is intact. Tests must ALWAYS run against LexAI_test.
  4. Run tests before pushing: Run python -m pytest -v. Do not push if it's below 86/86.
  5. Preserve Document Isolation: When writing database queries, ALWAYS include .filter_by(user_id=current_user.id) to prevent users from seeing other people's data.
  6. Keep Frontend/Backend separate: Put business logic in services/, route definitions in routes/, and UI in templates/.

30. Project Limitations

  • Gemini API Limits: Heavy usage by multiple simultaneous users will exhaust the free-tier API limits quickly.
  • Local Storage: Uploaded files and ChromaDB vectors are currently stored locally on the server disk. This makes load-balancing across multiple servers difficult without moving to cloud object storage.
  • No Replacement for Professionals: The AI can hallucinate or misinterpret complex jurisdictional nuances. LexAI explicitly warns users that it is an assistant, not a lawyer.
  • OCR Missing: It cannot read scanned image PDFs, only text-based PDFs.

33. Glossary

  • LLM (Large Language Model): An AI trained on massive amounts of text, capable of generating human-like responses (e.g., Gemini).
  • ORM (Object-Relational Mapper): A tool (like SQLAlchemy) that lets developers query a database using Python instead of raw SQL.
  • Embedding: A mathematical representation (vector array) of text, allowing computers to measure semantic similarity.
  • Chunk: A small piece of a larger document, broken down so it fits within an AI's token limit.
  • JSON: A standard text format for structuring data, used for API communications and structured AI outputs.
  • RBAC (Role-Based Access Control): Restricting system access based on the user's role (admin vs. user).
  • XSS (Cross-Site Scripting): A vulnerability where attackers inject malicious scripts into web pages. Prevented in LexAI using DOMPurify.
  • HTTP 429: A status code indicating "Too Many Requests" (Rate Limit hit).
  • HTTP 503: A status code indicating the service is temporarily overloaded or unavailable.
